# App de Gestión Operativa del Club — UNCAS Rugby

Aplicación interna para el cuerpo técnico y organizativo. Digitaliza procesos hoy manejados por WhatsApp, planillas y documentos físicos. ~60 usuarios activos, 17 planteles.

## Roles de usuario

| Rol | Responsabilidad |
|---|---|
| **Subcomisión** | Órgano directivo. Visión global. Admin del sistema. |
| **Coordinador** | Gestiona calendario y divisiones infantiles/juveniles. |
| **Entrenador** | Toma asistencia, registra lesiones, carga resultados. |
| **Manager** | Gestiona cobranzas y fichajes de su equipo. |
| **Secretaría** | Gestiona socios (alta, categorías, servicios, foto, estado) y publica noticias. |
| **Portería** | Escanea carnets QR de socios para validar acceso. |
| **Socio** | Ve su carnet digital QR, cuotas, noticias del club y sus servicios contratados. |

## Stack tecnológico

| Capa | Tecnología |
|---|---|
| Mobile | React Native + Expo (TypeScript) |
| Auth + DB + Realtime | Supabase (PostgreSQL, Auth, Storage, Edge Functions) |
| Push | Expo Push API desde Edge Functions |
| Offline | AsyncStorage + cola de sync (NetInfo) |
| Deploy mobile | Expo EAS — internal distribution (sin App Store en MVP) |
| Deploy web subcomisión | Next.js 16 → Vercel |
| Deploy web secretaría | Next.js 16 → Vercel (mismo repo, route group separado) |

**Bug crítico — freeze de iOS al abrir la app — RESUELTO (2026-08-14/15).** Testers de TestFlight reportaron que la app bloqueaba el teléfono apenas se abría, antes de llegar al login. Sólo en iOS — los mismos builds en Android sin problema. Cadena de investigación (dos teorías descartadas con evidencia directa antes de encontrar la causa real):
1. **Build 4 — teoría Face ID (descartada).** Sospecha inicial: crash por falta de `NSFaceIDUsageDescription`. Se agregó el plugin `expo-local-authentication` a `app/app.config.js` y `disableDeviceFallback: true` en `useLogin.ts`. Shippeado, **no resolvió nada** — un tester mandó un video del freeze real mostrando que pasa apenas se abre la app, antes de cualquier pantalla de login (el código de Face ID sólo corre al tocar un botón explícito).
2. **Teoría `aps-environment` dev/prod (descartada con evidencia de binario).** Se bajó el `.ipa` real y se inspeccionó el `embedded.mobileprovision` — el entitlement de push ya estaba en `production`, no era eso.
3. **Build 5 — red de seguridad, no fix real.** Se rastreó el freeze hasta `app/app/_layout.tsx`: el `SplashScreen.hideAsync()` queda condicionado a que `loading`/`rol`/`terminosLoading`/`restringidoLoading` resuelvan, y esa cadena depende de llamadas a Supabase sin ningún timeout. Se agregó un `setTimeout(...,8000)` que fuerza esconder el splash pase lo que pase (peor caso: cae al login en vez de pantalla negra infinita — `app/app/index.tsx` redirige ahí incondicional). Shippeado junto con un fix real de paso en `useCarnet.ts` (retry sin backoff). **Un tester en build 5 seguía con el freeze** — la red de seguridad no arregla la causa.
4. **Causa raíz real, encontrada con Opus + documentación oficial de Supabase.** El callback de `supabase.auth.onAuthStateChange` en `_layout.tsx` era `async` y hacía `await` de una query (`supabase.from('profiles')...`). Esa query necesita el mismo lock interno exclusivo que `GoTrueClient` todavía tiene tomado mientras espera a que el callback termine — espera circular, deadlock permanente. Es un bug documentado de `supabase-js`/`auth-js` (troubleshooting oficial de Supabase + issues `auth-js#762`, `supabase-js#2013`/`#1594`/`#2111`), no un tema de red ni de plataforma. Encaja con todos los síntomas: pasa en la ruta de restaurar sesión guardada (antes del login), no lo tocaban los fixes de Face ID ni de push, y es intermitente porque sólo se dispara cuando el token guardado ya venció (hace falta un refresh por red, que da tiempo a que el subscriber ya esté registrado cuando Supabase intenta notificar).
5. **Build 6 — fix aplicado.** El callback de `onAuthStateChange` volvió a ser sincrónico; la query de perfil se dispara con `setTimeout(...,0)` recién cuando el lock ya se liberó. De paso, `useTerminos.fetchEstado()` dejaba `loading` en `true` para siempre si no había sesión — el mismo tipo de bug, enmascarado hoy por el gate de sesión del splash pero real. Commits `90696c5` (Face ID), `ad19dfc` (timeout de splash), `bf61b09` (fix del deadlock + `useTerminos`) — **sin pushear a `origin` todavía**.

9. **Causa raíz real, encontrada con dos investigaciones de Opus en paralelo (issues de GitHub + documentación oficial de Apple/Expo): `app/assets/images/logo.png` medía 17286×21895px (~378 megapíxeles, 6.3MB), usado sin redimensionar en 5 lugares** (splash, login, Header, carnet, ícono Android/notificaciones).
